# MyHR — 제품 스펙

작성: 2026-09-09. Trainthon(연세대 AI 창업캠프 999) 해커톤 MVP.
이 파일이 제품의 정본이다. 구현은 이 문서를 따른다.
버린 대안과 이유는 [DECISIONS.md](DECISIONS.md), 마감·체크리스트·심사 Q&A는 [PITCH.md](PITCH.md).

---

## 1. 한 줄

**당신은 당신 네트워크의 CEO다. MyHR은 그 회사의 인사팀이다.**

앱을 열면 평범한 연락처 목록이다. 딱 하나 다르다 — **맥락이 검색된다.**

---

## 2. 문제

살면서 사람은 많이 만난다. 세상은 작아졌는데, 기억은 따라가지 못한다. 특히 창업가·학생·비즈니스를 하는 사람은 소개·행사·동아리·인턴을 넘나들며 인맥이 빠르게 는다.

진짜 페인은 「사람을 잊어버린다」가 아니라 **특정 순간**이다.

1. **재회 직전 5초** — 카톡이 오거나 행사장에서 마주쳤는데, 이 사람 누구였지, 어디서 봤지, 최근에 무슨 일이 있었지가 안 떠오른다.
2. **소개받고 싶을 때** — 내 연락처는 리스트지 네트워크가 아니다. 「이런 사람 누구 있지」를 머릿속으로 못 푼다.
3. **관계 유지 실패** — 좋게 알게 된 사람인데 몇 달이 지나면 끊긴다. 팔로업 타이밍을 아무도 안 알려준다.

기존 해법의 실패:

| 도구 | 남는 것 | 죽는 이유 |
| --- | --- | --- |
| 전화번호부 | 이름·번호 | 근황·관계·맥락을 기억하지 않음 |
| 수첩·메모 앱 | 직접 적은 칸 | 입력 마찰. 안 적으면 데이터가 없음 |

MyHR의 승부: **이미 하는 행동(카톡 캡처, 짧은 메모)을 사실 한 줄로 바꿔 저장**해서, 나중에 SQL·질문으로 꺼낸다. 폼을 채우게 하지 않는다.

---

## 3. 누구를 위한 제품인가

- **누구나.** 사람을 많이 만나고 이름을 잊는 순간이 있는 사람이면 된다. 창업가·심사역·대학생은 인맥이 빨리 느는 **예시**일 뿐, 제품 자체는 그 직군에 묶이지 않는다.
- **첫 사용 장면**: 대학 창업 동아리·학회·해커톤처럼 소개가 잦은 곳 — 트레인톤 참가자가 자연스러운 첫 후보다.
- **이번 해커톤의 실제 사용자**: 무대 데모용 **본인 시드 그래프 하나**. 참가자가 만져볼 수는 있게 하되, 무대 시드를 오염시키면 안 된다.

## 4. 제품이 하는 일 (세 기둥)

### 4.1 저마찰 입력

사용자가 칸을 채우지 않는다. 흔적을 던지면 AI가 `{person, key, value}` 문장 목록을 뽑는다.

v1 입력:

- 텍스트 붙여넣기 / 메모
- 카톡·명함 **이미지** (비전 모델이 UI째 읽음. 별도 OCR 엔진 없음)
- 음성: 마이크 버튼은 보여도 됨. **음성 API는 시간 남을 때만.** 데모 와우를 음성에 걸지 않는다.

쓰지 않는 것 (v1): 구글/아이클라우드/폰 주소록 동기화, 안드로이드 공유시트, 캘린더 연동.

카톡 캡처에서 뽑는 것: 방 제목, 말풍선 좌우(누가 말했는지), 근황/약속/제3자 소개, 관심사. 이미지는 **서버에 안 남기고** 추출 후 폐기. 남는 것은 `notes.raw_text`와 `attributes` 행이다.

### 4.2 사실 저장 (속성 테이블이 핵심)

사람을 저장하는 표가 아니라 **문장을 저장하는 표**다. 한 줄 = 사실 하나.

```
attributes (person_id, key, value, source)
```

컬럼은 처음부터 끝까지 이 네 개다. 「재희가 축구한다」가 세상에 처음 등장해도 `ALTER TABLE`이 아니라:

```sql
INSERT INTO attributes (person_id, key, value, source)
VALUES (5, 'plays_soccer', 'true', 12);
```

DB는 `plays_soccer`가 새 타입인지 모른다. `works_at`과 같은 글자다. 6개월 뒤 `has_pets`가 나와도 앱 재배포 없이 INSERT 한 줄이다. 스키마를 사람이 미리 그리지 않고, **AI가 키 목록을 키운다.**

`/extract`를 부를 때마다 **지금까지 쓰인 키 목록**을 프롬프트에 넣는다. 있으면 재사용 (`plays_soccer`), 진짜 없는 개념만 새 키.

같은 키를 다른 사람에게 재사용하면 쿼리가 산다:

```sql
SELECT person_id FROM attributes
WHERE key = 'plays_soccer' AND value = 'true';
```

와우 「축구 11명」「매운거 잘 먹음」은 이 조회다. 30명 산문을 매번 LLM에 넣는 검색이 아니다.

### 4.3 네트워크에 묻기

검색창은 사람을 **찾는다** (목록이 걸러짐).
FAB 질문은 인맥에게 **물어본다** (답변 시트 + 근거).

같은 `/api/ask`를 쓰고 `mode`만 나눈다.

## 5. 데이터 모델 (v1에서 만드는 표)

### 5.1 `people` — 누구인가 (목록용)

| 컬럼 | 역할 |
| --- | --- |
| `id` | 안정 id. 시드는 고정 문자열 또는 UUID. 신규는 저장 시 발급 |
| `name` | 표시 이름 |
| `photo_url` | 없으면 이니셜 |
| `tags[]` | 커뮤니티 필터: 주식동아리 / 농구동아리 / 셰플러 / 트레인톤 |
| `one_liner` | 목록에 보이는 한 줄. 속성 칸이 아님. extract가 짧게 갱신 |
| `updated_at` | |

전화번호 컬럼은 v1에 없다. 「연락처 800개」연출은 **이름만 있는 더미 행**으로 한다. 더미는 `one_liner` 비움, `attributes` 없음. AI 프롬프트·속성 쿼리에 안 넣는다.

본인 노드: `me`가 `people.id` 하나를 가리키는 한 행.

### 5.2 `notes` — 원본 입력

| 컬럼 | 역할 |
| --- | --- |
| `id` | note id. `attributes.source`가 이걸 가리킴 |
| `person_id` | 이 노트가 묶인 사람. 그룹방이면 **사람마다 행을 복제**해도 됨 (`raw_text` 동일) |
| `raw_text` | 추출된 글. 이미지 바이너리는 없음 |
| `source` | `'seed'` \| `'kakao_screenshot'` \| `'text'` \| `'voice'` |
| `created_at` | |

### 5.3 `attributes` — 사실 (정본)

| 컬럼 | 역할 |
| --- | --- |
| `person_id` | |
| `key` | 문자열. 스키마가 아님. 예: `works_at`, `likes_spicy`, `plays_soccer` |
| `value` | 문자열. 예/아니오는 `'true'` / `'false'` |
| `source` | `notes.id` |

한 `(person_id, key)`의 **현재 값**은 최신 행(또는 같은 키 UPDATE)이다. 이직·부상처럼 번복되면 새 노트에 묶여 값이 바뀐다. `plays_soccer=false`는 「행이 없는 사람」과 다르다. 축구 11명 쿼리(`=true`)에서 빠지지만, 「모른다」가 아니라 「안 한다」다.

해커톤 시드에 반드시 심을 키:

- `likes_spicy` = `'true'` — 와우 B
- `plays_soccer` = `'true'` — 와우 C, **11명 이상**

`/extract` 기본 키 목록에 이 둘을 포함해 동의어(`futsal`, `축구`)로 새 키가 안 생기게 한다.

### 5.4 `relationships` — 사람들 사이

| 컬럼 | 역할 |
| --- | --- |
| `from_id` | |
| `to_id` | |
| `label` | 예: `소개` |
| `source` | note id 또는 `'seed'` |

엣지는 사람 문서 안에 넣지 않는다. 사람 카드에 표시만 한다. 엣지 전용 스와이프 카드는 없다.

### 5.5 v1에서 안 만드는 표

이벤트 테이블, 임베딩/pgvector, 키 별칭 테이블, EAV 정규화 UI, 그래프 DB.

상세 화면의 「브리핑」은 `one_liner` + 그 사람 `attributes` + 이웃 엣지면 충분하다. 긴 dossier 마크다운 컬럼은 **필수 아님.** 목록/브리핑용 산문이 필요하면 `one_liner`만 유지한다.

## 6. 입력 파이프라인

항상 같은 루프.

1. 캡처 또는 텍스트 → `notes` 초안 (아직 people에 안 붙을 수 있음)
2. `POST /api/extract`에 실어 보냄:
   - 이미지 또는 텍스트
   - 현재 people 목록 (`id`, `name`) — 엔티티 해소
   - **현재 속성 키 목록** (distinct `attributes.key`)
3. 모델 출력 (Zod로 고정):

```ts
{
  people: { id?: string; name: string; tags?: string[]; one_liner?: string }[]
  attributes: { person: string; key: string; value: string }[]  // person = id 또는 이름
  edges: { from: string; to: string; label: string }[]
}
```

4. **사람 단위 스와이프 카드.** 오른쪽 = 그 사람의 people upsert + 그 사람 attributes INSERT + 그 사람 관련 edges. 왼쪽 = 버림.
5. 자동 저장 없음. 틀린 키가 한 번 들어가면 다음 키 목록을 오염시킨다.
6. 그룹방 한 장 → 데모는 **카드 3장**이 나오게 캡처를 맞춘다.

기존 사람이면 카드에 **이번 노트에서 생긴 사실 줄**을 보여 준다 (before 값 → after 값). 새 사람이면 이름 + 추출된 줄. 탭하면 사람 바꾸기·키/값 수정 (엔티티 해소 실패 탈출구).

`/extract`는 한 번만 짠다. 계약은 「노트 읽고 `{person, key, value}` 목록 뱉어. 있는 키면 재사용.」 그 다음 `has_pets`든 `coffee`든 코드를 안 고친다.

## 7. 질의 파이프라인

`POST /api/ask` 하나.

| UI | mode | 출력 |
| --- | --- | --- |
| 검색창, 이름 | 로컬 substring | 즉시 목록 필터. LLM 없음 |
| 검색창, 맥락 | `search` | 목록이 걸러짐 + 행마다 근거 한 줄 |
| FAB 질문 | `ask` | 시트. 답 + 근거 + 사람 칩 |

와우 B/C는 가능하면 **SQL 먼저**:

- 「매운거」→ `likes_spicy = true`
- 「축구 11명」→ `plays_soccer = true` 상위 11

매핑이 안 되는 질문만 people 30명(더미 800 제외)의 `one_liner` + 그 attributes + edges를 프롬프트에 넣는다.

검색창은 2~4초가 걸릴 수 있다. 이름 매칭을 먼저 띄우고, 아래에 `AI 검색 결과`가 채워지게 한다. 근거 없는 이름만 뜨면 그냥 느린 검색이다.

## 8. 화면 (트로이 목마)

설계 기준은 예쁜 제품이 아니라 **5분 데모**다.

**만들지 않음:** 로그인, 온보딩, 설정, 랜딩.

폼팩터: **390px 폭**, 데스크탑 페이지 중앙에 폰 프레임. 레이아웃 하나. 스와이프는 마우스 드래그로도 동작.

```
/                      연락처 목록
  상단 필터             전체 · 주식동아리 · 농구동아리 · 셰플러 · 트레인톤
  검색바                이름 즉시 + AI 검색
  행                    사진/이니셜 · 이름 · one_liner
  FAB 질문              → 답변 시트 (프리셋 칩)
  FAB 정보 추가         → 입력 → 스와이프

/person/[id]            상세 — 한 줄, 속성, 공통 지인, 노트 타임라인
                        (목록 직후 stub이라도 탭이 죽으면 안 됨)

/api/extract
/api/ask
```

화면 초안의 직장/가족 필터는 **이번 시드와 안 맞다.** 해커톤 필터는 커뮤니티 태그.

정보 추가의 이미지는 드래그앤드롭 + 전역 `paste` (카톡 캡처 → `Ctrl+V` → 즉시). 파일 선택 다이얼로그를 여는 순간 「마찰이 있다」를 스스로 증명한다.

그래프 캔버스는 주 화면이 아니다. 여유 있으면 토글. 없어도 상세의 **공통 지인**이 관계 데이터의 증거다.

프리셋 질문 칩 (무대에서 타이핑 안 함):

- 이번 주말 축구 할 사람 11명 뽑아줘
- 매운거 잘 먹는 사람
- 다음 주에 김재희 만나는데 브리핑해줘

## 9. 시간순 예시 (재희)

표 구조는 한 번도 안 변한다.

**9/9** 메모 「재희 핀테크 다님」 → `INSERT (5, works_at, 핀테크 스타트업, note#1)`

**9/12** 「재희 매운거 엄청 좋아함」 → 키 목록에 `works_at`만 있음 → `INSERT (5, likes_spicy, true, note#7)`

**9/20** 「재희랑 풋살 뛰었는데 잘하더라」 → `plays_soccer` 세상 첫 등장 → `INSERT (5, plays_soccer, true, note#12)`  
일반 사람 표였으면 여기서 `ADD COLUMN plays_soccer` + 나머지 전원 NULL.

**9/25** 「민수도 축구 함」 → 키 목록에 이미 `plays_soccer` → `INSERT (8, plays_soccer, true, note#20)`

이제 축구 명단 쿼리가 재희·민수를 고른다.

## 10. 데모 (무대 우선, 참가자는 가볍게)

우선순위: **무대 피칭**. 참가자가 URL을 열어 목록·검색·캡처 한 장을 만질 수 있으면 충분하다.

참가자와 무대가 **같은 라이브 DB에 쓰면** 시드의 `likes_spicy` / `plays_soccer`가 더러워져 피칭이 깨진다. 참가자 쓰기는 그 브라우저만이거나, 무대 직전 시드 리셋.

### 60초에 보여줄 와우

B 또는 C. 둘 다 살린다. 시간은 `/ask`(또는 SQL) 다음에 쓴다.

- B: 검색 「매운거 잘 먹음」→ 재희 등 + 근거
- C: 「주말 축구 11명」→ 명단

캡처 스와이프는 증명용. 무대 캡처는 **이름 안 겹치는 새 사람 3장**이 병합 실수보다 안전하다.

### 5분 스크립트

1. 연다. 평범한 목록. 설명 없음. (원하면 「800명 중 맥락 있는 건 30명」— 화면의 더미가 그 말)
2. 「매운거 잘 먹음」검색. 「이건 연락처 앱에서 안 됩니다.」
3. 더미 카톡 붙여넣기 → 스와이프 3장 → 목록에 행이 생김
4. 「축구 11명」→ 명단 + 근거
5. (시간 있으면) 상세 공통 지인 또는 그래프 한 컷
6. 비전: 모든 사람의 인간관계 기억 레이어

### 빌드 순서 — 어디서 멈춰도 데모가 성립

| # | 만들 것 | 여기서 멈추면 |
| --- | --- | --- |
| 1 | 목록 + 커뮤니티 필터 + 시드 30 + 더미 이름 + 이름 검색 + 상세 stub | 1막 |
| 2 | FAB 입력 + `/extract` + 스와이프 저장 | 입력이 도는 앱 |
| 3 | 속성 쿼리 + `/ask` 검색 (매운거) | 와우 B |
| 4 | FAB 질문 (축구 11명) | 와우 C |
| 5 | 상세 공통 지인 | 그래프 논거 |
| 6 | 그래프 토글 | 있으면 좋고 없어도 됨 |

잠긴 순서: **2까지 먼저.** 3~4가 무대 와우라서, 2가 끝나면 **바로 `/ask`(또는 SQL 검색)** 이 다음이다.

## 13. 차별점 · 사업 · 확장

기본 연락처에는 맥락이 없다. 수첩·메모는 칸을 채워야 한다. MyHR은 캡처가 입력이고, 사실 줄·사람들 사이 엣지가 쌓일수록 다른 데서 못 산다.

사업 모델(피칭용, 해커톤에서 결제 미구현): 일반 AI Pro처럼 **일정 무료 한도** 후, 더 많은 정보 입력·질의는 **토큰/사용량**으로 과금.

확장(v1 이후): 캘린더 연동으로 사람↔일정까지 묶기. 기기 성능·보안 요구가 올라가면 추출·질의를 **온디바이스 AI**로 옮기는 경로.

## 14. 아직 열린 것 (구현을 막지 않음)

- 이름 MyHR 유지 (B2B HR 오인 리스크는 태그라인으로 상쇄)
- Supabase vs 시드 JSON: 쓰기 보존이 필요하면 깨어 있는 Supabase + 리셋. 없어도 시드로 데모는 됨
- 빠른 저장(스와이프 생략): v1 없음. Q&A에서 「실사용은 신뢰 후 생략」이라고 답함
- `one_liner` 갱신: 추출 승인 시 그 사람만 다시 씀
